usage-guard: make Claude Code aware of your usage limits

Claude Code can't see your plan's 5-hour and weekly limits. It will start a big milestone at 92% and die mid-edit, leaving half-applied refactors, nothing committed and no notes. usage-guard gives Claude that awareness, and stays silent until it matters.

How it works

usage-guard escalates in steps. Each level is triggered by a usage percentage or by the projected minutes left at your current pace, whichever comes first.

UsageWhat Claude is toldWhat else happens
NormalNothing. Zero tokens.
Conserve ≥75%, or ~45 min leftWork lean: targeted reads, no broad exploration or subagents, commit after each finished task.Status line turns yellow.
Wrap-up ≥88%, or ~20 min leftWrite HANDOFF.md and commit it now. Then continue only in small committed steps, keeping the hand-off current.New subagents are blocked. If Claude tries to end a turn with uncommitted work and no hand-off, it is sent back once to finish them.
Critical ≥95%, or ~8 min leftStart nothing new. Make sure the hand-off is current and committed, tell the user, and stop.
Limit hitClaude can't act any more.The plugin writes an emergency snapshot to HANDOFF.md without the model: branch, uncommitted files, your last request, open tasks. You also get a desktop notification.
After resetOne line: a recent HANDOFF.md exists, so read it before continuing previous work.

Every message tells Claude which window it is (5-hour or weekly), the usage percentage, the projected minutes left and the reset time. That lets Claude make sensible calls: if the window resets in 10 minutes, it suggests pausing instead of handing off. For a model-specific weekly limit, it suggests switching models.

Tested end to end with Claude Code

The test gave Claude an 8-task milestone with usage at 89%, then raised it to 96% after about 20 seconds. Claude:

  1. Told the user about the limit, wrote the plan to HANDOFF.md and committed it.
  2. Implemented T1, T2 and T3, with one commit each and the backlog boxes ticked.
  3. When the critical warning arrived, used one tool call to rewrite HANDOFF.md with exact next steps and gotchas, then committed wip: checkpoint before usage limit.
  4. Stopped and reported: "T1–T3 done; T4–T8 not started; hand-off in HANDOFF.md."

Any agent can pick up from there.

Where the numbers come from

  1. The status line feed (preferred). Claude Code gives status line commands rate_limits.five_hour and rate_limits.seven_day (used_percentage, resets_at) after every API response, on Pro and Max plans. Hooks don't receive this data, so /usage-guard:setup records it to a small shared cache that the hooks read. This costs no tokens and no network calls.
  2. The usage endpoint (fallback). Without the tap, a detached background process reads the same endpoint /usage uses, with your existing Claude Code login. It polls at most every 5 minutes (2.5 minutes once usage is elevated), backs off on HTTP 429, never refreshes your token, and is skipped for Bedrock, Vertex, Foundry and custom base URLs.

The cache is account-wide, so several Claude sessions running in parallel all see the shared burn.

Burn-rate projection. A raw percentage misleads: 85% with three hours left can be fine, while 70% burning 2% a minute is about to run out. usage-guard keeps a short history of readings and projects the minutes until the limit. That projection can escalate earlier than the percentage thresholds, and it can hold back a hand-off when the window will reset before you would run out.

Why it stays cheap

  • No always-on context. No MCP server, no CLAUDE.md, and every skill is disable-model-invocation, so not even a skill description sits in context. At normal usage the plugin adds 0 tokens.
  • Escalation-only messages. Each level is announced once (the full wrap-up message with the hand-off protocol is about 225 tokens), with a one-line reminder every 15 tool calls at wrap-up or above.
  • Fast hooks. About 40 ms each, stdlib Python, no network in the foreground. Every failure path exits silently, so the plugin can never block or break a session.
  • The emergency snapshot is written by a script, not the model, because by then there's no budget left to spend.

The hand-off file

HANDOFF.md sits at the repo root and is written for a reader with no context: Codex, a human, or a future Claude session. It has these sections:

  • Goal: the overall task or milestone, and where its spec or backlog lives.
  • Done: completed items, with commit hashes.
  • In progress: exact files and functions touched, and what's left.
  • Next steps: concrete and in order.
  • Decisions and gotchas: choices made and why, traps found, things not to retry.
  • Verify: the commands that prove the work.

To continue elsewhere, tell the other agent: "Continue the work described in HANDOFF.md." If the limit hits before Claude finishes the protocol, an auto-captured block between <!-- usage-guard:auto:start/end --> markers still records what changed and what was open.

Configuration

The main options are prompted when you enable the plugin and can be changed under /config. All options can also go in ~/.claude/usage-guard.json, or per project in .claude/usage-guard.json:

{
  "notice_pct": 75, "wrapup_pct": 88, "critical_pct": 95,
  "notice_eta_min": 45, "wrapup_eta_min": 20, "critical_eta_min": 8,
  "wrapup_policy": "incremental",
  "handoff_file": "HANDOFF.md",
  "auto_commit": true,
  "block_subagents": true,
  "api_fallback": true,
  "statusline_segment": "always"
}
  • wrapup_policy: incremental (default) hands off early and keeps working in small committed steps, so the remaining budget gets used. stop stops starting work at wrap-up.
  • auto_commit: set to false if Claude must never commit. The hand-off note is still written.
  • api_fallback: set to false to make the plugin fully offline.

Set USAGE_GUARD_DISABLE=1 to switch the plugin off for one shell. The README lists every option.

Privacy, network and files

  • Runs: a single stdlib Python script with your local Python 3, plus read-only git commands. It installs and downloads nothing.
  • Network: one request type only, GET https://api.anthropic.com/api/oauth/usage, the endpoint Claude Code's own /usage reads. Sent only by the fallback poller and never when the status line tap is feeding data. No telemetry or analytics.
  • Credentials: for that request only, the poller reads Claude Code's existing OAuth token from Claude Code's own store. It is never logged, stored, refreshed or sent anywhere else.
  • Writes: only the hand-off file in your project, plus readings in the plugin's data directory. /usage-guard:setup backs up ~/.claude/settings.json before editing its statusLine. The plugin never pushes.

FAQ

How do I stop Claude Code from getting cut off mid-task by the usage limit?

Install usage-guard. It tells Claude where it is in the 5-hour and weekly windows, so as the limit approaches Claude works lean, commits in small steps and writes a HANDOFF.md before it is cut off. If the limit still hits, a script writes an emergency snapshot.

Can I hand off from Claude Code to Codex or another agent?

Yes. HANDOFF.md is written for a reader with no context. Run /usage-guard:handoff, then tell the other agent to continue the work described in HANDOFF.md.

Does usage-guard work on Windows?

Yes, as long as Python 3 is on your PATH. macOS and Linux have it out of the box; on Windows, install it from python.org.

What happens if I have extra usage credits enabled?

If extra usage is enabled, hitting the limit bills credits rather than stopping you. Claude is told so, and the thresholds stay the same.
